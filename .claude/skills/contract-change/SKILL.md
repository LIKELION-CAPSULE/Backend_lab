# 계약 변경: 확장 → 이전 → 제거

상대는 지금 이 순간에도 옛 계약으로 코드를 쓰고 있다. 계약을 제자리에서 바꾸면 상대 브랜치는 머지하는 순간 깨진다. 그래서 세 번에 나눠 바꾼다. 각 단계는 **별도 PR**이고, 어느 PR도 상대 브랜치를 깨뜨리지 않는다.

## 1단계 확장 (추가만)
- 새 메서드/새 DTO 필드/새 이벤트를 **추가**한다. 기존 것은 그대로 둔다.
- 기존 것에 `@Deprecated(forRemoval = true)` + Javadoc `@deprecated <대체 메서드> 사용. 제거 예정 PR: (2단계 후)`.
- DTO(record)에 필드를 더할 때는 기존 생성자를 유지하는 보조 생성자를 둔다.
- DB: 새 컬럼 추가(nullable 또는 기본값). 기존 컬럼 유지. `scripts/new-migration.sh`.
- PR 본문 '리뷰 요구사항'에 "계약 확장: 옛 X는 Y로 대체 예정" 명시.

## 2단계 이전
- 호출하는 쪽을 새 계약으로 옮긴다. 내 모듈 호출부는 내가, **상대 모듈 호출부는 상대에게 요청**(또는 합의 후 cross-module PR, 상대에게 공유).
- DB: 데이터 백필 마이그레이션, 코드가 새 컬럼을 읽고 쓰게.

## 3단계 제거
- `grep -rn "<옛 이름>" src/`로 사용처가 0인지 확인 후 옛 계약 삭제.
- DB: 옛 컬럼 삭제 마이그레이션.
- develop에 두 사람의 이전이 모두 머지된 뒤에만.

## 예외: 아직 아무도 안 쓰는 계약
`grep`과 열린 PR(`gh pr list`, 각 PR diff 검색)에서 사용처가 없으면 한 번에 바꿔도 된다. 단 PR 본문에 "사용처 없음 확인(방법)"을 적는다.

## 상대에게 남길 한 줄 (카톡/PR 댓글)
`[계약 변경] <모듈>.<이름>: <옛> → <새>. 1단계 PR #<번호>. 2단계에서 네 쪽 호출부 <파일> 옮겨줘/옮겨도 될까?`
