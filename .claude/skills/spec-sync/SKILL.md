# 명세 고치기와 노션 사본 반영

원본은 레포 `docs/specs/api.md`·`schema.sql`이다(ADR 0013). 노션은 프론트·기획이 보는 **읽기 전용 사본**이다. 흐름은 한 방향뿐이다: 레포 → 노션.

## 전제
- 노션 반영에는 Claude Code의 Notion MCP가 필요하다. 노션 도구가 없으면 멈추고 안내한다:
  `claude mcp add --transport http notion https://mcp.notion.com/mcp` → Claude Code에서 `/mcp`로 로그인
- 노션 위치와 마지막 반영 커밋은 `docs/specs/SOURCE.md`에 있다.

## A. 명세 바꾸기 (명세 PR)
1. develop에서 `feature/spec-<설명>` 브랜치를 만든다.
2. `api.md`·`schema.sql`만 고친다. 기존 형식(섹션 머리, 표, 코드 블록)을 그대로 따르고, 바꾼 곳 근처에 `> yyyy-mm-dd: 무엇을 바꿨나` 한 줄을 남긴다. 기획 판단이 필요한 값은 지어 넣지 않고 "확정 필요"로 표시한다.
3. 영향 범위를 뽑는다. 명세 PR에는 코드를 넣지 않는다:
   - API 변경 → `python3 .harness/zones.py spec-impact` (바뀐 API → 컨트롤러 · 모듈 · 담당). DTO · 서비스 · 테스트는 그 컨트롤러에서 따라가 찾는다
   - 스키마 변경 → 필요한 새 마이그레이션 목록 (기존 마이그레이션은 수정 금지)
4. 이 변경만 담은 작은 PR을 pr-write로 올린다. 본문 '작업 내용' 끝에 `### 코드 반영`을 둔다. api.md를 바꾼 PR은 이게 비면 CI가 빨개진다(ADR 0015)
   - 영향받는 모듈마다 한 줄: 기능 PR · 이슈 번호(`#12`), 브랜치(`feature/...`), 또는 `없음 (이유)`
5. 코드 반영까지 이어서 한다 (명세만 바뀌고 코드가 남지 않게):
   - 명세 브랜치 위에 `feature/<모듈>-<설명>` 브랜치를 만들어 고친다. 명세에 맞게 DTO · 서비스 · 검증 · 테스트까지 바꾸고 verify. 기능 PR은 명세 PR 다음에 머지한다(명세 PR이 머지되면 `git rebase origin/develop`)
   - 남의 모듈이어도 직접 고친다(구역 훅의 확인 질문을 거침). 기능 PR '리뷰 요구사항'에 cross-module과 바뀐 파일을 적고 담당자에게 한 줄 공유. 담당자가 그 모듈에서 같은 곳을 작업 중이면(열린 PR · 브랜치) 고치지 말고 담당자에게 할 일 목록을 넘긴다
   - 기능 PR 번호를 명세 PR 본문 `### 코드 반영`에 적는다 (`gh pr edit <명세 PR> --body-file ...`)
6. 상대에게 한 줄 공유. 사람에게는 명세 PR · 기능 PR 링크와 바꾼 파일을 보고한다.

## B. 노션 사본 반영 (명세 PR이 머지된 뒤)
1. `git fetch` 후 `SOURCE.md`의 '노션 사본 반영' 커밋부터 develop까지 바뀐 부분을 본다:
   `git diff <반영 커밋> origin/develop -- docs/specs/api.md docs/specs/schema.sql`
2. 노션 상위 페이지를 먼저 읽어 맨 위 '레포 기준 커밋'이 SOURCE.md와 같은지 본다. 노션에서 누가 고친 흔적(레포에 없는 내용)이 보이면 **덮어쓰지 말고 멈추고 사람에게 알린다.** 명세 PR로 옮길지 사람이 정한다.
3. 바뀐 곳만 반영한다:
   - `## <순서>. ...` 섹션 → 인라인 DB에서 같은 '순서'의 행. 속성(분류·설명·와이어프레임)과 본문
   - `## 공통 규칙` → 상위 페이지의 '공통 규칙' 섹션
   - `schema.sql` → DB 페이지의 SQL 코드 블록 (맨 위 안내 주석은 빼고)
   - 노션 형식으로 옮긴다: `` `x` `` → `<code>x</code>`, `**x**` → `<b>x</b>`, `> ✅ ...` 같은 인용은 기존 콜아웃 모양에 맞춤. 요약하거나 고쳐 쓰지 않는다
   - 목표 페이지를 먼저 fetch하고, 바뀐 문장만 `update_content`로 바꾼다(전체 덮어쓰기는 피함)
4. 노션 상위 페이지와 DB 페이지 맨 위의 '레포 기준 커밋'을 새 develop 커밋으로 바꾼다.
5. 같은 커밋을 `SOURCE.md`의 '노션 사본 반영' 줄에 적어 작은 PR로 올린다(다음 명세 PR에 같이 넣어도 된다).

## 하지 말 것
- 노션에서 고치고 레포로 가져오기 (방향이 반대)
- 명세 사이의 불일치(API ↔ DB)를 반영하면서 몰래 고치기. 명세 PR로 고친다
- 노션에 레포에 없는 내용을 추측해서 채우기
