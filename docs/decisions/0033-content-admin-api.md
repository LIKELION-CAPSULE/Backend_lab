# 0033 모델 · 메이트 등록은 관리용 API로 (콘텐츠를 마이그레이션으로 넣지 않는다)

- 결정
  - content 모듈에 관리용 API `/internal/content/**`를 둔다
    - `POST /internal/content/models`: 모델 하나(경로 · `format` · 크기 · 위치)와 그 표정 · 모션 · 반응표를 한 트랜잭션으로 넣고 새 모델 id를 준다
    - `POST /internal/content/mates`: 새 메이트(이름 · 한 줄 소개 · 소개 · 해시태그 · 모델). 모델이 없으면 준비 중 메이트
    - `PUT /internal/content/mates/{id}/model`: 메이트의 모델을 바꾼다(새 버전으로 교체)
  - 인증은 고정 토큰 `Authorization: Bearer <토큰>`. 토큰은 환경변수 `CAPSULE_CONTENT_ADMIN_TOKEN`(설정 `capsule.content.admin.token`)으로만 넣고, 값이 없으면 이 API와 보안 체인이 아예 생기지 않는다(운영에서 잊고 열리는 일이 없게)
  - 부르는 쪽은 모델 제작 도구 Aliving2D의 '캡슐에 올리기': 모델 묶음을 Supabase 버킷(ADR 0024)에 `<이름>/v<번호>/`로 올린 뒤 이 API로 등록한다. 서버 주소 · 토큰은 Aliving2D 쪽 PC에만 둔다
  - ADR 0016 '남은 일'의 "운영 DB의 콘텐츠 데이터는 content 담당이 마이그레이션으로 넣는다"를 이것으로 바꾼다. 예시 시드(`db/seed`)는 로컬 · 테스트용으로 그대로
- 이유
  - 메이트 모델을 Aliving2D로 계속 만들고 새 버전도 자주 올린다(2026-11-23 결정, 새 모델 기본 형식 `ALIVING2D_V2`). 그때마다 SQL을 쓰고 PR을 올리면 번거롭고, 경로 오타 · 표정 이름 불일치 같은 실수가 난다
  - 서버가 등록할 때 형식 · 경로 · 표정 이름 · 반응표가 가리키는 표정과 모션을 검사하므로 잘못된 행이 들어가지 않는다
- 버린 대안
  - 매번 마이그레이션(지금까지의 계획): 기록은 git에 남지만 콘텐츠 하나마다 PR이 필요하다
  - Supabase DB에 직접 INSERT(서비스 키): 서버의 검사를 건너뛰고, 스키마가 바뀌면 조용히 깨진다
  - 실험실(`/internal/llm-lab`)에 붙이기: 실험실은 운영에서 꺼져 있다(ADR 0027)
  - 관리자 로그인(ADR 0027 계정)으로 받기: 도구가 부르는 API라 매번 로그인하는 것보다 고정 토큰이 간단하다. 사람이 쓰는 관리 화면이 생기면 그때 계정 로그인을 붙인다
  - 관리자 웹 화면: 지금은 쓰는 곳이 Aliving2D 하나라 API로 충분하다
- 대가
  - 운영 DB의 콘텐츠 행이 git 기록으로 남지 않는다. 등록할 때 서버 로그에 남기고, Aliving2D가 올린 기록(작업 폴더 `capsule.json`)을 가진다
  - 토큰이 새면 그 사람도 모델 · 메이트를 등록하거나 바꿀 수 있다(사용자 · 대화 데이터는 못 본다). 환경변수로만 두고 HTTPS로만 부른다. 새면 서버 환경변수를 바꾸면 예전 토큰은 바로 무효
  - 새 메이트의 대화 설정(`characters/<code>/profile.yml`, ADR 0022)은 이 API가 만들지 않는다. 대화가 되려면 설정 파일을 따로 넣어야 한다
