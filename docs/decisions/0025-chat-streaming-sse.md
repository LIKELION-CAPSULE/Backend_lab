# 0025 채팅 답장은 SSE로 흘려 보낸다 (Spring MVC SseEmitter, 명세 28)

- 결정
  - 채팅 답장을 만들어지는 대로 보내는 API를 새로 둔다: `POST /api/sessions/{sessionId}/messages/stream` (명세 28). 20번은 그대로 둔다(프론트가 옮기는 동안 둘 다)
  - 응답은 SSE(`text/event-stream`). `reply` = 지금까지의 대사 전체(조각이 아님), 마지막 `done` = 20번 응답 전체, 스트림을 연 뒤 오류는 `error`
  - Spring MVC의 `SseEmitter`로 만든다. 답장은 가상 스레드에서 만들고, LLM 공급자의 스트리밍(`onText`, 이미 있음)에서 받은 원문 JSON에서 대사만 꺼내(`ReplyStream`) 보낸다. JSON 없이 글로만 쓴 답은 그 글이 대사이고, 끝에 붙은 `emotion=…`은 그 이름이 캐릭터 감정일 때만 말풍선에서 빼고 감정으로 쓴다(`SceneChatPipeline.plain`, 실제 키 확인 9번 중 1번)
  - 검증 · 재전송 · 속도 제한(`DialogueService.accept`)은 스트림을 열기 전에 한다: 그 오류는 보통 JSON 에러 응답이라 프론트의 기존 처리를 그대로 쓴다
  - 대체 대사 기준: 첫 대사를 llm-budget(7초, 2026-11-06까지 5초) 안에 못 보내면 대체 대사. 첫 대사를 보낸 뒤에는 끝까지 기다린다(상한은 LLM http-timeout). 이미 보인 글을 대체 대사로 바꾸지 않으려고
- 이유
  - 20번은 답장이 다 만들어질 때까지(1.5~2.5초) 아무것도 안 보여 느리게 느껴졌다(승희 2026-11-05). 로컬 gpt-5 측정: 첫 글자 1.0~2.0초, 전체 1.8~2.5초. 첫 글자부터 보이면 체감이 ChatGPT와 같아진다
  - SSE는 한 방향 텍스트 스트림이라 이 용도에 충분하고, 프록시(Railway · 프론트 Cloudflare Worker · Vite)를 그대로 통과한다. 프론트 프록시가 `accept: application/json`을 붙여도 스트림이 온다(로컬 확인)
  - `reply`에 전체 글: 게이트웨이가 재시도하거나 공급자를 바꾸면 글이 처음부터 다시 온다. 전체 글이면 프론트는 받은 값으로 바꾸기만 하면 된다
  - 표정 · 호감도는 `done`에서: 표정은 대사와 같은 LLM 답에서 나와 대사가 끝나야 확정된다. 답장 형식(JSON 키 순서)을 바꾸는 프롬프트 변경을 피했다
- 버린 대안
  - WebFlux(`Flux<ServerSentEvent>`): 앱 전체가 MVC · JPA라 리액티브 스택을 하나 더 들이는 값이 크다. 가상 스레드 + SseEmitter로 충분하다
  - WebSocket: 양방향이 필요 없고, 인증 · 프록시 설정이 더 든다
  - 20번 응답을 바꾸기: 프론트가 옮기기 전까지 지금 화면이 깨진다(계약은 확장 → 이전 → 제거)
  - 조각(delta)만 보내기: 재시도로 글이 처음부터 다시 오면 프론트가 겹쳐 붙인다
- 대가
  - 요청 하나가 답장이 끝날 때까지(보통 2~3초, 길면 30초) 연결을 잡는다. 가상 스레드라 스레드 수는 문제가 아니지만, Tomcat 연결 수 · 프록시 시간 제한(프론트 60초, SseEmitter 50초) 안에서 돈다
  - 첫 대사를 보낸 뒤에는 마감 대체가 없어 아주 느린 답은 그대로 기다린다(http-timeout 30초가 상한)
  - 표정이 대사 끝에 바뀐다. 대사 시작과 함께 바꾸려면 LLM이 감정을 먼저 쓰게 프롬프트를 바꿔야 한다(이후 필요하면)
