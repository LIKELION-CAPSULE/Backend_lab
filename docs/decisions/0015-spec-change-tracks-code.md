# 0015 명세가 바뀌면 코드 반영까지 추적 (0013 보완)

- 결정
  - `zones.py spec-impact`: `api.md`에서 바뀐 섹션(`## N. METHOD 주소`)을 컨트롤러의 `@RequestMapping` + `@XxxMapping` 주소와 맞춰 컨트롤러 · 모듈 · 담당을 찾는다. 공통 규칙처럼 API가 아닌 섹션은 "사람이 확인"으로 표시한다
  - `api.md`를 바꾼 PR은 본문 '작업 내용'에 `### 코드 반영`이 있어야 한다. 영향받는 모듈마다 기능 PR · 이슈 번호, 브랜치, 또는 `없음 (이유)`. 없으면 pr-zones가 실패한다
  - spec-sync 스킬: 명세 PR 위에 기능 PR을 이어서 올린다. 남의 모듈도 명세를 바꾼 사람이 직접 고치고(구역 훅 확인 질문, cross-module) 담당자에게 공유한다. 담당자가 같은 곳을 작업 중일 때만 넘긴다
  - 처음엔 남의 모듈은 이슈로 넘기려 했으나, 명세를 바꾼 사람이 맥락을 가장 잘 알고 이슈는 반영을 늦춘다는 판단으로 직접 고치기로 함(2026-11-04, 첫 적용: #35 → #37)
- 이유
  - 0013 이후 명세 PR은 "영향만 정리하고 코드는 고치지 않는다"였다. 코드 반영은 사람이 기억해야 했고, 잊으면 명세와 코드가 어긋난 채 남는다(2026-11-04 메시지 전송 `characterId` 변경에서 지적)
  - 영향 범위를 모델 판단이 아니라 명령으로 찾으면 매번 같은 결과가 나온다(0005: 규칙은 구조에)
- 버린 대안
  - 명세와 코드를 한 PR에: "명세 PR 먼저 머지"(0013)와 모듈 담당 구분이 깨짐. 남의 모듈 코드가 내 명세 PR에 섞임
  - OpenAPI 생성 + oasdiff로 명세 · 구현 비교(0013 2단계): 정확하지만 새 의존성과 CI 단계가 필요. 구현이 명세를 따라잡으면 그때 붙인다. 이 결정은 그 전까지의 장치
  - 스킬 절차만 바꾸고 CI 검사 없음: GitHub 웹에서 고친 명세나 다른 세션에서 놓침
- 대가
  - spec-impact는 주소만 맞춘다. 요청 · 응답 필드가 실제로 맞는지는 기능 PR과 리뷰가 본다
  - 주소를 문자열 상수로 쓰거나 컨트롤러 이름이 `*Controller.java`가 아니면 "구현 없음"으로 나온다. 지금 명세 23개 API는 모두 찾음(2026-11-04)
