# 0013 명세 원본을 git(docs/specs)으로, 노션은 읽기 전용 사본 (0008 대체)

- 결정: API 명세(`docs/specs/api.md`)와 DB 스키마(`docs/specs/schema.sql`)의 원본은 레포다. 명세를 바꿀 때는 이 파일을 고치는 작은 명세 PR을 올리고 기능 PR보다 먼저 머지한다. 노션은 프론트·기획이 보는 **읽기 전용 사본**이고, 명세 PR이 머지되면 spec-sync 스킬이 노션에 반영한다.
- 이유: 노션은 두 사람과 여러 Claude 세션이 동시에 고치면서 꼬였다(2026-11-03~04 하루에 spec-sync 5~7차, 노션 직접 수정과 스냅샷이 엇갈림). 노션에는 리뷰, 충돌 표시, 누가 왜 바꿨는지가 남지 않는다. git에서는 명세 변경도 PR로 리뷰되고 diff·이력·충돌이 보이며, 코드와 같은 흐름을 탄다. 0008이 지키려던 것(에이전트·CI·리뷰어가 같은 버전을 봄)은 그대로다.
- 노션 사본 규칙
  - 상위 페이지(시연 API 최종본)와 DB 페이지 맨 위에 "읽기 전용 사본, 레포 기준 커밋"을 적는다. spec-sync는 그 커밋부터 바뀐 부분만 반영하고 커밋을 갱신한다
  - 노션에서 누가 고친 흔적이 보이면 되돌리지 않고 사람에게 알린다. 명세 PR로 옮길지 사람이 정한다
- 2단계 (구현이 명세를 따라잡으면): springdoc으로 코드에서 OpenAPI를 자동 생성하고, PR에서 oasdiff로 깨지는 변경을 검사한다
  - `api.md`는 구현 전 설계(행동 규칙, 와이어프레임 대조)를 담는 원본으로 남는다. OpenAPI는 실제 구현된 계약(요청·응답 모양)의 기록이다
  - 생성된 OpenAPI 파일을 레포에 두면 PR diff로 실제 계약 변화가 보이고, oasdiff가 develop의 파일과 비교해 프론트를 깨는 변경(필드 삭제, 타입 변경, 필수 추가)을 잡는다
  - 새 의존성(springdoc)과 CI 단계가 생기므로 붙일 때 이 ADR에 버전과 실행 방법을 덧붙인다
- 버린 대안
  - 노션 원본 유지(0008): 위 이유로 꼬임
  - 노션 보관 + GitHub 링크만: 동기화가 없어 가장 단순하지만 프론트·기획이 GitHub을 봐야 함
  - 노션을 기획 초안으로 두고 백엔드가 git으로 옮기기: 옮기는 단계가 하나 더 생기고, 노션과 git 중 어느 쪽이 최신인지 다시 헷갈림
  - OpenAPI를 원본으로: 구현 전 설계와 행동 규칙(휴식 중 무시, 5초 대체 대사 등)을 담기 어렵다. 2단계에서 구현 기록으로만 쓴다
  - `/api/v1` 주소 버전: 배포된 옛 앱이 없고 프론트·백엔드를 같이 배포해서 지금은 부담만 늘어남. 외부 클라이언트가 생기면 다시 본다
- 대가: 명세를 고치는 사람이 마크다운 PR을 써야 한다. 노션 반영을 잊으면 프론트가 옛 명세를 본다 → 노션 맨 위의 '레포 기준 커밋'으로 얼마나 뒤처졌는지 보이게 한다
