# 0034 음성(TTS)은 OpenAI TTS, 28 스트리밍에 문장 단위로 흘려 보낸다

- 결정
  - 메이트 답장 음성은 메시지 스트리밍(28)에서만 준다. LLM 글이 나오는 대로 문장 끝(첫 조각은 쉼표도)에서 잘라 TTS에 넘기고, 돌아오는 mp3를 SSE `audio` 이벤트(`seq` · base64)로 바로 보낸다. 끝나면 `audio_end`. 20(한 번에 받는 응답)은 음성을 주지 않는다
  - 공급자는 `TtsClient` 인터페이스 뒤에 둔다. 구현은 OpenAI(`/v1/audio/speech`, 응답 본문을 받는 대로 넘김)와 가짜(무음 조각). `capsule.tts.provider`로 고르고 기본은 가짜라 로컬 · 테스트 · 개발 서버는 비용이 들지 않는다. 키는 LLM과 같은 `OPENAI_API_KEY`
  - 켜지는 조건: 요청 `tts` + 설정 `voiceEnabled` + 크레딧(보이스 20, 고급이면 50). 아니면 음성 없이 글만. 보이스 20은 LLM 답장이 성공한 턴만 고급 모드와 한 줄로 깎는다(같은 requestId 한 번). 대체 대사 · 안전 경고 턴은 음성은 주고 깎지 않는다
  - 메이트별 목소리는 운영 설정 `capsule.tts.voices`(메이트 id → OpenAI 목소리 이름), 없으면 `capsule.tts.voice`
- 이유
  - 답장을 다 만든 뒤 음성을 만들면 LLM 시간 + 음성 시간을 모두 기다린다. 글이 나오는 대로 문장마다 음성을 만들면 첫 소리까지 = 첫 문장 + 첫 조각 음성 시간이라 답이 길어도 빨리 말한다(음성 대화 서비스의 일반적인 방식)
  - 28이 이미 SSE로 글을 흘리고 있어 이벤트 하나를 더하는 것으로 끝난다. 프론트도 이미 그 스트림을 읽는다
  - OpenAI는 이미 LLM 공급자로 쓰고 있어 키 · 계정이 있고, 다른 음성 서비스보다 값이 싸다(유료). 정해진 목소리만 고를 수 있지만 베타에는 충분하다
- 버린 대안
  - 20 응답에 `audioBase64`로 같이 넣기(원래 명세): 음성을 다 만들 때까지 글도 늦게 뜬다
  - 답장 뒤 `GET /audio`로 따로 받기: 글은 빠르지만 첫 소리가 답장 전체 + 음성 시간 뒤라 느리다
  - 음성↔음성 실시간 모델(OpenAI Realtime 등): 가장 빠르지만 캐릭터 설정 · 결정 모델 · 호감도 · 안전 검사를 거치는 지금 대화 흐름을 우회한다
  - ElevenLabs · Cartesia(WebSocket 입력 스트리밍): 더 빠르고 목소리가 좋지만 새 계정 · 비용. `TtsClient` 구현만 더하면 바꿀 수 있다
- 대가
  - 문장마다 HTTP 요청이 하나씩이다(답장 하나에 보통 2~6번). 조각 사이 이음새가 아주 짧게 들릴 수 있다
  - 크레딧은 음성 생성이 끝나기 전에(답장 저장 때) 깎는다. 음성이 중간에 실패해도 되돌리지 않는다(`audio_end.complete` false). 확정 필요
  - 잔액은 음성을 켤 때 보고 답장 저장 때 깎는다. 그사이 다른 요청이 먼저 써서 모자라지면 음성은 이미 나가는 중이라 그대로 두고 보이스 몫은 깎지 않는다(고급+보이스면 고급 30만). 크레딧 규칙 '그 기능만 멈춤'과 같은 쪽
  - 남은 음성을 기다리다 시간이 넘으면 더 보내지 않지만, 이미 보낸 OpenAI 요청은 HTTP 한도까지 돈다
  - OpenAI 목소리는 영어 기반 다국어라 한국어 억양이 어색할 수 있다. 메이트별 목소리 · 공급자는 들어 보고 정한다(J-10)
