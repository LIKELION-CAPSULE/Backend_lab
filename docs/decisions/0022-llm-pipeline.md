# 0022 LLM 파이프라인: 공급자 중립 게이트웨이, DB 프롬프트 버전, 실험실

- 상태: 실험 (2026-11-04, `feature/dialogue-llm-pipeline`에서만. develop에 넣기 전에 승희·성욱이 확인)
- 결정
  1. **LLM 호출의 입구는 `LlmGateway` 하나.** 서비스·대화 엔진·실험실은 용도(`LlmPurpose`: CHAT · DIRECTOR · ACTOR · JUDGE · REACTION · SUMMARY · CLOSING · EVAL_JUDGE)만 말한다. 게이트웨이가 공급자·모델·한도를 정하고, 재시도(429·5xx·연결 오류) → 대체 공급자 → 호출 기록(`llm_usages`)을 맡는다. 모델 거절(refusal)은 다른 공급자로 넘기지 않고 대체 대사로 끝낸다(안전 판단 우회 방지).
  2. **공급자 전환은 설정 한 줄** (`capsule.llm.provider`: fake · anthropic · openai). 용도에는 모델 이름 대신 등급(fast · smart · judge)을 적고, 등급 → 모델 표는 공급자마다 둔다. 키는 환경변수(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`)로만.
  3. **공급자 어댑터는 SDK 없이 Spring `RestClient`(JDK HttpClient)로 직접 HTTP.** Anthropic Messages API, OpenAI Chat Completions(같은 형식의 다른 서버도 base-url로). 일반 호출과 스트리밍(SSE) 모두. 형식은 로컬 가짜 서버 테스트(`LlmProviderTest`)로 고정한다.
  4. **프롬프트는 DB 버전(`prompt_versions`)에서 읽는다.** 코드는 키(`PromptKey`)로 찾는다. 고칠 때는 새 버전(DRAFT) → 실험실에서 고정(pin)해 시험 → ACTIVE. 이전 ACTIVE는 ARCHIVED, 되돌리기 = 예전 버전 다시 켜기. 캐릭터 전용 버전이 공통 버전보다 먼저. 호출마다 쓴 버전 id가 `llm_usages.prompt_version_ids`에 남는다.
     - 공통 프롬프트의 원본은 git의 시드(`classpath:prompts/`). 시작할 때 같은 본문의 공통 버전이 없으면 새 ACTIVE로 넣는다: 처음엔 버전 1, 시드 파일을 고쳐 배포하면 그 본문이 새 ACTIVE. 운영에는 실험실이 없으므로 운영 프롬프트는 이 길로만 바뀐다(SQL 손작업 없음). 실험실에서 좋았던 본문을 시드 파일로 옮겨 커밋하는 것이 "내보내기"다.
     - 캐릭터 전용(대화 엔진 파일 등)은 시드가 없고 실험실에서 올린다.
  5. **답장(명세 20) 파이프라인은 두 개.** SIMPLE: 명세 그대로 LLM 한 번(답장 + 감정 + 호감도 JSON). ENGINE: #11 대화 엔진(감독 → 배우 [→ 품질 모드 후보 3 + 심사]). 서비스는 `capsule.dialogue.chat-pipeline`으로, 실험실은 대화방마다 고른다. 같은 코드를 부르므로 실험실 품질 = 서비스 품질.
  6. **엔진 상태는 `dialogue_states`** (세션 × 캐릭터, jsonb + 낙관적 잠금 + 형식 버전). 턴이 성공했을 때만 저장, 공부 종료 때 삭제.
  7. **LLM은 DB 트랜잭션 밖에서.** 메시지 전송은 읽기 → LLM(5초) → 저장(한 트랜잭션).
     - 저장 트랜잭션은 호감도(`applyChat`)부터 부른다. applyChat은 relation 행을 잠그고, 공부 종료도 정산 때 같은 행을 잠근 채 커밋까지 간다. 그래서 답하는 사이 종료가 겹치면 종료가 끝난 뒤 세션을 다시 보고 409 `SESSION_ENDED`, 답장·호감도·엔진 상태·답 못 받은 사용자 말을 남기지 않는다. 잠금 순서가 종료(세션 → relation → 대화)와 같아 교착이 없다.
     - 같은 requestId가 처리 중이면 끝날 때까지 기다렸다가 같은 답장(명세 20). 사용자 말을 저장한 지 8초가 지나도 답이 없으면(먼저 온 요청이 죽음) 기다리지 않고 이어받는다.
     - 서비스 호출에는 마감(5초)이 붙는다. 마감이 지나면 게이트웨이가 새 호출(재시도·대체 공급자·엔진의 다음 단계)을 시작하지 않는다(결과가 버려질 호출에 돈을 쓰지 않음). 이미 보낸 호출은 끝까지 받아 실제 지연을 기록한다.
     - 공부 종료(22)는 session의 트랜잭션 안이라 요약과 완료 대사를 동시에 보내 5초 안에 끝낸다.
  8. **실험실 `/internal/llm-lab`** (local에서만 켬): 실험 대화방(연속 대화 + 턴마다 원문·지연·비용·사람 평가), 한 번 실행(같은 입력 N번), 프롬프트 버전 관리, 평가(골든 대본 × 반복, LLM 심사 0~10, 사람 1~5, 실행끼리 비교), 호출 집계(p95 지연, 5초 초과 수).
     - 보안: 전용 보안 체인, 기본 거부. 화면 주소만 열고, API는 토큰(`capsule.llm.lab.token`)이 비어 있으면 이 컴퓨터(loopback) 요청만, 넣었으면 `X-Lab-Token` 헤더가 같아야 한다.
  9. **원칙: LLM은 고르기만 하고, 숫자는 코드가 정한다.** 대사는 LLM이 쓰고, 감정은 후보 중에서 고르고, 호감도는 사용자 말의 **신호**(`ChatSignal`: NEUTRAL · PRAISE · STUDY_WILL · STRUGGLE · RUDE · ABUSE)만 고른다. 신호 → 점수 · 하루 상한은 relation의 `AffinityPolicy`가 정한다(J-06). 답장 JSON에서 `affinity` 점수를 뺐다.
  10. **결정 입구 `Decider` + 용도 DECIDE.** 상태 글 + 보기가 정해진 질문 → 보기 하나 + 확신도. 게이트웨이를 지나므로 재시도 · 기록 · 마감이 같다. 공급자는 용도별로 고를 수 있다(`routes.DECIDE.provider`): TypeSafe **Jev**(결정 모델, `JevProvider`)로 보내고, Jev가 실패하면 기본 LLM이 같은 질문에 답한다. 기본값은 비워 둬서 LLM(fast 등급)이 결정한다. 신호 읽기는 답장과 **동시에** 나가고(`ChatReplier`), 답장이 끝났을 때 마감이 지났으면 기다리지 않고 NEUTRAL. 확신도가 `signal-min-confidence`(0.6)보다 낮으면 NEUTRAL.
  11. **호감도는 0~100 (%처럼).** 쌓이는 점수가 아니라 끝이 있는 값이다. 범위를 넘는 몫은 잘라 실제로 바뀐 만큼만 `relation_logs`에 남긴다(기록 합 = 지금 점수). DB CHECK 0~100(relation 마이그레이션). 단계 기준도 %로(임시 0 · 30 · 70), 공부 시간은 10분당 +1(임시). API 필드 이름(`points`)은 그대로, 뜻만 0~100.
  12. **상태 반응은 두 갈래.** 동작 이벤트(DROWSY · YAWN · WAVE · HEAD_TURN)는 고정 대사 + 모션(LLM 없음, 캐릭터별 · 호감도 단계별 대사 묶음에서 무작위). 상태 변화(GREETING · AWAY · RETURN · BREAK · BREAK_END)는 LLM이 호감도 단계 · 지난 요약 · 이번 세션 최근 대화(6줄)를 보고 쓴다. 5초를 넘기면 같은 칸의 고정 대사.
  13. **호감도 최종안 (2026-11-04 PM 결정 + 승희 조정). 9 · 11을 대신한다.**
      - 호감도(캐릭터가 나를 어떻게 보는가)와 레벨(함께 공부한 시간)을 나눈다. 호감도 0~100 · 50에서 시작, 관계 단계 = 호감도 구간(0 · 30 · 70 · 90, 내려가면 같이 내려감). 레벨 = 자리 지킴 60분당 1(상한 없음).
      - 호감도를 바꾸는 것은 대화 · 자리 비움 · 연속 출석뿐. 공부 시간 점수 · 첫 만남 +5 · 돌아옴 +1 · 동작 이벤트 점수는 없앴다.
      - 대화: 말의 종류(`SignalType` 8종)를 **말 패턴으로** 고른다(A안, `ChatScorer`, 엔진 `Rules`의 패턴 + THANKS · HATE_OR_SEXUAL). 점수표는 설정(`capsule.dialogue.chat-scores`, 캐릭터별 표는 말포이 콘텐츠를 앱으로 옮길 때). 세션 안 규칙(고민 1번 · 무례 반복 −3 · 같은 종류 10턴 안 세 번째 0)은 dialogue가, 하루 상한 · 0~100 · 그날 오름 멈춤은 relation이 한다.
      - **오르기는 어렵고 내려가기는 쉽다**: 오르는 쪽만 하루 +15. 혐오 · 성적은 지금 값의 −30%(최소 −5)이고 그날은 더 오르지 않는다. 비율 감점이라 오탐이 비싸서, 패턴이 걸리면 결정 모델이 한 번 더 확인한다(0.8 미만이면 무례 −2).
      - 결정 모델 분류(B안)는 `signal-detector: DECIDER` 한 줄로 켠다(다음 주 재검토, 같은 점수표).
      - 자리 비움: `AWAY`를 끝낸 상태 이벤트에서 session이 비운 시간을 넘기고(`SessionEventRef.awaySeconds`), 1분 넘으면 −1 · 하루 최대 −3. 연속 출석: 세션 첫 FOCUS가 그날 출석, 2일째부터 하루 +1.
      - 숫자는 모두 설정(`capsule.relation`, `capsule.dialogue`). PM 답이 오면 값만 바꾼다.
  14. **대화 기억은 세 겹이고 모두 크기가 정해져 있다.** ① 아는 사실(`character_memories`, 최대 20개) ② 지난 세션 흐름(`conversation_recaps`, 최근 5장) ③ 이번 세션 원문(최근 20줄). 세션이 쌓여도 프롬프트 크기가 같다.
      - ①은 매 턴 답장을 보낸 뒤 결정 모델이 무시 · 추가 · m고치기 · m지우기 중 하나를 고르고(Mem0의 ADD · UPDATE · DELETE · NOOP), 추가 · 고치기면 LLM(MEMORY 용도)이 40자 한 줄로 쓴다. 20개를 넘으면 결정 모델이 오늘 날짜 기준 가장 덜 중요한 하나를 골라 버린다. 전화번호 같은 긴 숫자는 묻지 않고 저장하지 않는다.
      - ②는 공부 종료 때 **그 세션만** 카드 한 장(코드가 "11/03 55분" 머리말, LLM이 70자 안팎 흐름). 지난 카드를 다시 압축하지 않고, 6장째부터 오래된 것을 지운다. 오래 남길 사실은 ①이 이미 뽑았으므로 흐름은 잊어도 된다. 카드 쓰기에 실패하면 메시지를 남겨 다음 종료 카드에 같이 넣는다.
      - 쓸지 말지는 답장 모델이 정한다(ChatGPT 저장 메모리처럼 매번 넣고, 프롬프트 규칙: 이어질 때만 · 이미 꺼낸 기억은 다시 안 꺼냄 · 확실하지 않으면 물어봄). `conversations.summary`는 더 쓰지 않는다.
  15. **세계관 · 캐릭터 설정은 DB 데이터, 답장은 장면 카드(SCENE) 파이프라인 (2026-11-04, 승희).** 첫 캐릭터는 말포이(PM 확정).
      - 테이블(dialogue 모듈): `worlds` · `world_lore` · `world_events` · `character_profiles`(정체성 · 화법 · 절대 규칙 · 안전 기준 · 표정 · 대체 표정 · 관계 단계 말투) · `character_moves`(대화 기술 + 어울리는 말의 종류) · `character_lines`(상황별 미리 쓴 대사, 순서대로) · `character_scores`(대화 점수표) · `character_habits`(피할 말버릇). `characters`(content)는 화면용 정보만.
      - 처음 값은 git의 `classpath:characters/<code>/`(profile.yml + 엔진 형식 character.yml)에서 **DB가 비어 있을 때만** 불러온다(`CharacterContentSeeder`). 그 뒤로는 DB가 원본이고 실험실 API(`/internal/llm-lab/api/characters/{id}/content`, GET · PUT, reseed)로 고친다. 운영에도 같은 길로 들어간다(Flyway 시드가 안 도는 운영에서도).
      - SCENE: 코드가 이번 턴에 쓸 것만 고른다. 키워드가 맞는 지식 ≤4장, 말의 종류에 맞는 대화 기술 1개 + 예시 2개, 가끔 세계 사건 1개, 아는 사실 ≤3개(글자 겹침), 세션 카드 ≤2장, 관계 단계 말투 한 줄, 일정은 세션 첫 대화에만, 피할 말버릇. LLM은 한 번: [바이블 · 규칙 · 세계 · 표정(매번 같아서 캐시)] + [장면 카드] + 이번 세션 대화. 설정이 없는 캐릭터는 SIMPLE로 넘긴다.
      - 상태 반응 · 5초 대체 대사 · 완료 대사는 그 캐릭터의 `character_lines`가 있으면 그것(순서대로, PM 확정), AI 상태 반응은 `reaction-llm-triggers: []`로 끈다. 표정 에셋이 없으면 `expression_fallbacks`로 대신.
      - 대화 점수표는 `character_scores`가 있으면 그것, 없으면 설정의 기본 표.
- 이유
  - 공급자를 아직 못 정했다(OpenAI · Claude). 고른 뒤에도 장애 대비 대체 공급자가 있으면 좋다. 용도 → 등급 → 모델 두 단계면 공급자를 바꿔도 코드·용도 설정은 그대로다.
  - 기획(말투·길이·호감도·요약)이 미정이라 프롬프트가 계속 바뀐다. 배포 없이 바꾸고, 바꾼 것이 품질·비용에 준 영향을 버전별로 비교해야 한다(호출 기록에 버전 id).
  - "몇 번 돌려 보고 괜찮다"는 느낌으로 정하면 다음 수정 때 나빠져도 모른다. 같은 대본을 같은 잣대(고정된 심사관 + 사람 점수)로 다시 돌려 숫자로 비교한다.
  - LLM이 점수를 직접 내면 같은 말에 점수가 흔들리고, 테스트할 수 없고, 칭찬 반복으로 쉽게 오른다(J-06 ②). 분류만 맡기면 기획 점수표를 그대로 코드로 옮기고 하루 상한을 걸 수 있다. 엔진의 사용자 말 분석과도 같은 모양이라 ENGINE으로 바꿔도 점수 규칙은 같다.
  - 분류는 글을 쓰지 않는 작은 결정이라 결정 모델(Jev)이 빠르고 싸다(입력 요금만). 다만 2026-09 얼리 액세스 제품이고 한국어 성능을 확인하지 못해서, LLM이 기본이고 Jev는 실험실 평가로 비교한 뒤 켠다(같은 코드, 설정 한 줄).
  - 0~100은 합의된 기획 방향이다(쌓이기보다 "지금 얼마나 가까운지"). 범위를 자르면서 기록도 실제 변화로 남겨야 정산 · 리포트 · 단계 계산(기록 합 기준)이 어긋나지 않는다.
  - 동작 이벤트는 자주 오고 즉시 떠야 해서 고정 대사, 상태 변화는 드물고 태도 변화가 보여야 해서 LLM (합의).
  - (13) 사람 관계처럼 호감은 쌓기 어렵고 한 번에 꺾인다. 고정 점수로 깎으면 100에서 심한 말을 해도 −5라 거의 안 변한다. 비율로 깎으면 높을수록 크게 꺾이고, 하루 상한 때문에 며칠에 걸쳐 천천히 돌아온다(승희).
  - (13) 패턴(A안)은 매번 같은 결과라 PM이 점수표를 읽고 바로 이해하고, 테스트로 고정할 수 있다(PM 확정). 결정 모델은 오탐이 비싼 곳(비율 감점)에만 확인용으로 쓴다.
  - (14) 다른 서비스 조사: ChatGPT는 사실 목록 + 최근 대화별 짧은 메모(약 15개) + 지금 대화 원문(토큰 한도에서 앞부터 잘림), 벡터 검색 없이 그대로 넣는다(밖에서 실험해 알아낸 구조). MemGPT는 넘친 대화를 기존 요약과 합쳐 다시 쓰는데(재귀 요약) 쓸수록 정보가 빠진다는 비판이 있다. Mem0은 새 사실마다 ADD · UPDATE · DELETE · NOOP을 고른다. 공부 앱 1:1 대화 규모면 검색 없이 작은 목록 두 개로 충분하다.
  - 명세의 5초 대체 대사 때문에 지연이 품질만큼 중요하다. 호출마다 지연·첫 글자 시간을 남겨 감독 끄기·모델 낮추기·스트리밍 전환을 숫자로 판단한다(#11 "먼저 재 본다").
- 버린 대안
  - **Anthropic Java SDK (#11에서 정했던 것)**: 공급자 두 개를 쓰려면 OpenAI SDK까지 두 개가 들어온다(둘 다 Kotlin·OkHttp·Jackson 2 의존. Boot 4의 Jackson 3와 버전 충돌 위험). 우리가 쓰는 기능은 메시지 호출·캐시 표시·사용량·스트리밍뿐이라 어댑터 두 개(각 150줄 안팎)로 충분하다. 구조화 출력·도구 사용 같은 새 기능이 필요해지면 그 공급자만 SDK로 바꿔도 `LlmProvider` 뒤라 다른 코드는 그대로다.
  - **Spring AI**: #11의 이유 그대로(엔진이 자체 포트를 가짐, Boot 4.1 호환 미검증) + 프롬프트 캐시 지점·캐시 토큰이 추상화 뒤로 숨는다.
  - **프롬프트를 git 파일로만**: 바꿀 때마다 배포해야 하고, 실험 중인 버전과 서비스 버전을 동시에 둘 수 없다.
  - **LiteLLM 같은 프록시 서버**: 운영할 서버가 하나 더 생긴다. 2인 팀에 과하다.
  - **답장 JSON에 신호까지 같이 받기(LLM 한 번)**: 호출이 하나 줄지만 답장 모델(smart)이 분류까지 해서 비싸고, 신호만 Jev로 바꾸는 실험을 할 수 없다. 동시 호출이라 지연은 늘지 않는다.
  - **프론트가 대사를 고르기 / 18 응답에 대사 넣기**: 4-9(노션), 위 결과·주의 참고.
  - **호감도를 계속 쌓되 화면에서 %로 나눠 보이기**: 기준(분모)이 바뀌면 모든 사용자의 %가 바뀐다. 끝이 있는 값으로 저장하는 쪽이 단순하다.
  - **엔진 상태를 `dialogue_session` + `dialogue_turn` 두 테이블로(엔진 명세)**: 턴 지표는 `llm_usages`(trace_id로 묶음)로 충분하다(#11 추천안과 같음).
  - **매 턴 LLM이 0~100 점수를 직접 매기고 보정**: 같은 말에 점수가 흔들려 PM이 "왜 이만큼"을 물어도 답할 수 없다. 종류를 고르고 숫자는 코드가 정하는 쪽으로(9의 원칙 유지).
  - **결정 모델이 매 턴 종류를 고르기(이 브랜치의 9 · 10)**: PM이 A안으로 확정. 코드는 남겨 `signal-detector: DECIDER`로 켤 수 있게 했다.
  - **내려가는 쪽도 하루 −10 상한 (PM 안)**: 심한 말에 바로 꺾이지 않는다. 승희가 오르는 쪽만 상한(+15)으로 바꿈 (PM 확인 필요).
  - **끝으로 갈수록 덜 오르게(곱하기 보정)**: 점수가 정수라 +1에 0.2를 곱하면 0이 된다. 하루 상한과 반복 0점으로 대신했다.
  - **관계 단계가 경계에서 덜 흔들리게(내려갈 때 5 여유)**: 단계를 따로 저장해야 해서 뺐다. 흔들림이 보이면 넣는다.
  - **요약 한 칸에 계속 합치기 / 넘치면 다시 압축(MemGPT)**: 끝없이 길어지거나 쓸수록 정보가 빠진다.
  - **기억을 쓸지 결정 모델이 먼저 판단**: 5초 안에 호출이 하나 늘고, 대화 흐름은 답장 모델이 가장 잘 안다.
  - **벡터 검색(RAG)**: 사실 20개 · 카드 5장이면 전부 넣어도 1천 자 남짓이다. 검색 서버 · 임베딩 비용이 더 크다.
  - **(15) 대화 엔진(#11 이식)을 기본으로**: 브라우저 프로토타입을 원본과 똑같이 옮기는 게 목표였어서 말포이 전용 내용이 코드에 있다("흥" · "아버지" 규칙, 에세이 진척 · 밤 · 머글 연구). 캐릭터를 늘릴 때마다 코드를 고쳐야 하고, 설정이 텍스트 덩어리라 DB에서 고칠 수 없다. 쓸 만한 방식(장면 카드만 넘기기, 대화 기술, 반복 금지, 세계 사건)만 데이터로 옮겼다. 엔진은 실험실 비교용으로 남기고, SCENE 품질을 확인한 뒤 지운다.
  - **(15) 캐릭터 설정을 content 모듈(성욱)에**: "콘텐츠"라는 이름엔 맞지만 이 데이터를 쓰는 곳은 대사뿐이고, 모듈 경계를 넘는 작업 · 기다림이 생긴다.
  - **(15) 설정을 JSON 한 칸(문서)으로**: 되돌리기는 쉽지만 세계 지식을 캐릭터끼리 나눠 쓸 수 없고 행 단위로 고칠 수 없다. 대신 실험실 API는 문서 모양(GET · PUT 한 번)으로 주고받는다.
  - **(15) 매 턴 감독 AI가 기술 · 지식을 고르기**: 호출이 두 번이라 5초가 빠듯하다. 코드 규칙으로 고르고, 감독은 품질 차이가 확인되면 켠다.
