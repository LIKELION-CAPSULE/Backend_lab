# 0028 표정은 대사를 다 쓴 뒤 결정 모델(Jev)이 캐릭터 표정 목록에서 고른다

- 결정
  - 답장(20 · 28)과 상태 반응(19)에서 LLM은 대사만 쓴다. 표정 지시를 프롬프트(`scene.system`)에서 뺀다
  - 대사가 끝나면 `ExpressionPicker`가 `Decider`(DECIDE 용도, 설정상 Jev)에 묻는다: 상태 = 사용자 말 + 대사, 보기 = 캐릭터 표정 목록(`character_profiles.expressions`), 보기 설명 = `expression_guide`(표정마다 언제 쓰는지)
  - `Decider`는 보기 밖 답을 버리므로 목록 밖 값은 나오지 않는다. fact-pick-wait(1.5초) 안에 못 고르거나 실패하면 null(표정을 바꾸지 않음). 답장의 마감(llm-budget 7초)과는 따로 기다린다(스트리밍은 첫 대사 뒤 마감을 넘겨 끝날 수 있음)
  - 지운 것: 목록 밖 감정 이름 · 에셋 없는 표정 대체 표(`expression_fallbacks`, 코드와 profile.yml. DB 칸은 배포 뒤 다음 마이그레이션에서), 대사 끝 감정 표시를 떼던 코드(`[emotion=…]` · `emotion=…`), 스트리밍 미리보기의 태그 숨김
  - 캐릭터 설정이 없는 캐릭터(공통 프롬프트, 공통 후보 HAPPY 등)는 그대로 JSON {content/reply, emotion}
- 이유
  - 프롬프트로 목록을 부탁하고 대체 표로 메우는 방식이 계속 샜다: 목록 밖 이름(걱정 · 질투), 풀어 쓴 값(`[emotion=자랑처럼 웃음과 경멸 사이, 결국 웃음]`)이 말풍선에 나감, Sonnet은 20번 중 5번 표시를 빼먹음(2026-11-06 로컬 실측)
  - 대사에 형식을 섞으면 대사가 딱딱해졌다(JSON 출력 때). 대사만 쓰게 하면 말이 가장 자연스럽다(SillyTavern도 표정은 대사를 보고 따로 분류한다)
  - 결정 모델은 이미 있다(기억 · 말의 종류 · 아는 사실 고르기). 보기 고르기 전용이라 빠르고(실측 약 0.2초) 보기 밖을 내지 않는다
- 버린 대안
  - LLM 함수 호출(`reply(text, expression: enum)`): enum이라 목록 밖은 막지만 대사가 다시 JSON 칸 안에 들어가고, 공급자마다 호출 형식 코드가 든다
  - 대체 표를 계속 늘리기: 모델이 쓰는 말은 끝이 없다
- 대가
  - 답장마다 결정 호출이 하나 늘어 `done`이 약 0.2초 늦다(첫 글자 속도는 그대로). Jev가 느리거나 실패하면 그 턴은 표정이 안 바뀐다
  - 표정 기준은 `expression_guide` 문구에 달렸다. 바꾸면 profile.yml 버전을 올린다
