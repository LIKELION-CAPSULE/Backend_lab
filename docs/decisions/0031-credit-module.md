# 0031 크레딧은 새 모듈 `credit`, 잔액은 지급 건 + 내역으로

- 결정
  - 12/1 베타 크레딧(출석 1,500 · 초대 1,000 · 보이스 · 고급 대화 차감)을 새 모듈 `credit`(담당 성욱)에 둔다. 테이블 `credit_grants`(지급 건마다 남은 양 · 소멸 시각) · `credit_ledger`(지급 · 사용 · 소멸 내역, 바뀐 뒤 잔액)
  - 다른 모듈은 `credit/api`만 쓴다: 조회(`CreditQuery`, 홈 · 내 정보 · 연결 시작의 `credits`), 쓰기(`CreditCommands`, 초대 보상 지급 · 대화 차감). 차감은 요청 id로 한 번만
  - 출석 지급과 지난 출석분 소멸은 배치 없이 그 사용자의 크레딧을 처음 읽거나 쓸 때 처리한다(하루 = 오전 5시 KST)
  - 차감은 소멸이 빠른 지급 건(출석분)부터 쓴다
- 이유
  - 크레딧은 회원 · 대화 · 초대가 모두 쓰는 돈 같은 값이라 한 곳에서 잔액과 내역을 지켜야 한다. user에 넣으면 대화 모듈이 user 내부까지 알아야 하고, dialogue에 넣으면 초대 보상(user)이 대화 모듈을 불러야 한다
  - 잔액 한 칸만 두면 "출석분은 다음 오전 5시에 사라지고 초대분은 안 사라진다"를 계산할 수 없다. 지급 건마다 남은 양을 두면 소멸 · 차감 순서가 명확하다
  - 배치를 두면 서버가 꺼져 있던 시간의 지급 · 소멸을 따로 메워야 한다. 읽을 때 처리하면 서버 1대 전제(ADR 0011)에서 잠금 하나로 끝난다
- 버린 대안
  - user 모듈 안에 두기: 테이블 수가 적어 빠르지만 대화 차감 때문에 dialogue → user 내부 의존이 커진다
  - `users.credits` 잔액 칸 하나 + 내역: 단순하지만 소멸 시각이 다른 두 종류를 나눌 수 없다
  - 매일 오전 5시 배치: 정확한 시각에 바뀌지만 놓친 날을 메우는 코드가 따로 필요하다
- 대가
  - 모듈이 하나 늘어 zones.conf · ModularityTests 대상이 늘어난다
  - 읽기 요청도 출석 지급 때문에 쓰기 트랜잭션이 된다 (사용자 행 잠금)
